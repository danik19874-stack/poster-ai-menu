# poster-ai-menu

ИИ-меню для маркетплейса Poster POS. Дизайн: `docs/superpowers/specs/2026-09-10-poster-ai-menu-design.md`.

TDD: on — сетевой многопользовательский продукт, обрабатывает чужие заказы и деньги (комиссия через агентский договор Poster). Зафиксировано 10.09.2026 по стандарту `~/.claude/skills/tdd/SKILL.md`, без отдельного вопроса владельцу — категория однозначно попадает в режим ON (сервер/API, чужие деньги).

11.09.2026 — гостевой флоу заказа (категории, `?table=`, корзина, оформление) прогнан вручную в браузере против реального подключённого аккаунта Poster: добавление в корзину, живой пересчёт, реальная отправка заказа (получен настоящий `incomingOrderId`), очистка корзины после отправки, и оба защитных состояния (стол не определён, корзина пуста) — все проверены визуально, не только по зелёным тестам. План: `docs/superpowers/plans/2026-09-11-guest-ordering-ui.md`.

11.09.2026 — админка (`/admin`) и пул ключей Gemini прогнаны вручную в браузере: вход без пароля редиректит на логин, неверный пароль показывает ошибку, верный пароль пускает и ставит cookie, добавление/выключение/включение ключа работает и сразу видно в таблице, `POST /api/admin/keys` без cookie реально возвращает 401. Отдельно подтверждено сквозным тестом: реальный гостевой заказ (через уже работающий флоу из плана выше) действительно попадает в `activity_log`, и админка сразу показывает актуальные «Заказов сегодня»/«Активны за 30 дней» — не только по зелёным тестам. `ADMIN_PASSWORD` в `.env.local` сейчас dev-заглушка (`changeme-dev-only`) — заменить на реальный пароль перед любым использованием вне локальной разработки. Найден (не исправлен в рамках этого плана, отдельная забота) хрупкий паттерн в уже существующем `app/menu-preview/[restaurantId]/cart/page.tsx` — React предупреждает про обновление состояния до монтирования компонента при резолве `params`; сам заказ прошёл корректно, но паттерн стоит переделать на `useEffect`. План: `docs/superpowers/plans/2026-09-11-gemini-key-pool-admin.md`.

11.09.2026 — фундамент i18n (next-intl, маршруты под `app/[locale]/`, раздельные root layouts для публичной части и админки) прогнан вручную в браузере после restructure. Проверено лично: (1) `/` рендерит полную русскую версию лендинга (шапка, hero с моков телефона, 4 карточки возможностей, «как это работает» со стеком телефонов, преимущества, тариф $15/мес, CTA-баннер, футер), URL остаётся без префикса; (2) `/en` — полный английский перевод, утечек сырых ключей вида `Hero.title` не найдено (проверено регуляркой по всему тексту страницы); (3) переключатель языка в шапке: клик по EN уводит на `/en` с английским контентом, клик по RU возвращает на `/` (не на `/ru`, хотя `href` у ссылки формально `/ru` — редирект на дефолтную локаль без префикса отрабатывает) с русским контентом; (4) регрессия по гостевому флоу через реальный `restaurantId` (`39b2e8f2-21bc-48cf-aaba-3492b0fd4bf2`) без локали в URL, как у настоящих QR-кодов: `/menu-preview/{id}?table=1` грузит реальные категории/блюда/фото из Poster, блюдо добавлено в корзину, на странице блюда открыт «Спросить» (поле ввода + сабмит-кнопка, изначально задизейблена, пока пусто), заданный вопрос вернул ожидаемый fallback «Сейчас сервис перегружен» (ключ Gemini не настроен — это ожидаемо), страница корзины показывает добавленную позицию и итог; (5) `/admin` без сессии редиректит на `/admin/login` (проверено с очищенными cookies — с валидной cookie от предыдущей сессии `/admin` отдаёт дашборд напрямую, что и ожидается); попыток логина с угаданным паролем не предпринималось; (6) `curl -sI /api/oauth/start` возвращает 307 на `https://joinposter.com/api/auth...`, не 404 и не связанную с локалями ошибку. Нетривиальный архитектурный факт на будущее: `/admin` и дерево `app/[locale]` — теперь два независимых root layout'а Next.js, а не один общий; любой UI, задуманный для обеих частей, нужно оформлять как общий компонент и импортировать в оба layout'а, а не добавлять в один root layout — общего слоя для этого больше нет. Также зафиксировано осознанное решение: `localeDetection: false` выставлен намеренно, чтобы гостевые QR-ссылки всегда отдавали русский независимо от языка телефона гостя; английский доступен только через явную навигацию (`/en`) или переключатель в шапке.

11.09.2026 — страница `/connected` (редирект после успешного OAuth вместо голого JSON) прогнана вручную в браузере: открыл с реальным `restaurantId` (`39b2e8f2-21bc-48cf-aaba-3492b0fd4bf2`) и настоящим именем заведения — карточка показывает имя, номер стола (по умолчанию 1), ссылку `/menu-preview/{id}?table=N` и живой QR-код (генерируется на клиенте через `qrcode`). Смена номера стола на 7 обновила и текст ссылки, и QR без перезагрузки страницы. Переход по сгенерированной ссылке подтверждён — открывает реальное гостевое меню («Стол 7 · меню синхронизировано с кассой»). Проверено на `/connected` и `/en/connected` — оба языка корректны. `completeOAuthConnection` теперь возвращает `restaurantId` (читается через `.select('id')` на upsert), `app/api/oauth/callback/route.ts` редиректит на `/connected?restaurant=...&name=...` вместо `NextResponse.json(...)`. Origin для ссылки строится на сервере из заголовков `host`/`x-forwarded-proto` (не через `window.location` в клиентском эффекте) — так страница не имеет hydration-рассинхрона и не зависит от порядка рендера.

11.09.2026 — найден и исправлен реальный пробел: `syncMenu` (подтягивает меню из Poster в кэш `menu_items`) существовал и был покрыт тестами, но нигде не вызывался в приложении — ни при OAuth-подключении, ни по таймеру/вебхуку. Для нового реального заведения после подключения `menu_items` остался бы пустым, и гость увидел бы пустое меню. Исправлено: (1) `completeOAuthConnection` теперь синхронизирует меню сразу после подключения (ошибка синка логируется, но не откатывает и не блокирует само подключение — заведение уже сохранено); (2) в админке добавлена секция «Заведения» со списком подключённых ресторанов, кнопкой «Обновить меню» (ручной ресинк, `POST /api/admin/restaurants/{id}/sync-menu`) и ссылкой «Ссылка и QR» на страницу `/connected` для повторного получения QR. Прогнано вручную в браузере на реальном подключённом ресторане: кнопка «Обновить меню» реально вызвала Poster API (~2.7с, видно по логам приложения), гостевое меню осталось рабочим после ресинка. Периодической автоматической синхронизации по-прежнему нет (только при подключении и вручную из админки) — если Poster даёт вебхук на изменение меню, стоит подключить отдельным планом.

12.09.2026 — реальный инцидент: единственный ключ Gemini в базе был тестовой заглушкой (`выключен`, 21 символ вместо 39 у настоящего ключа Google) — ИИ-консультант отвечал заглушкой «сервис перегружен» на каждый вопрос гостя, не потому что реально перегружен, а потому что рабочего ключа не было вообще. Владелец добавил свой первый настоящий ключ через `/admin`, но по ошибке вставил в поле значения свой пароль от админки вместо ключа Gemini (обнаружено прямым запросом к `gemini_api_keys` — значение совпадало с паролем admin, 24 символа, не начиналось на `AIza`). Обе плохие записи (тестовая заглушка и ошибочная) удалены из базы. Добавлена кнопка «Удалить» у ключей в админке (`POST /api/admin/keys/{id}/delete`) — раньше ключи из интерфейса убрать было нельзя вообще, только руками через базу. Прогнано вручную в браузере: добавлена одноразовая тестовая запись, кнопка «Удалить» реально убрала её из таблицы. На момент этой записи в базе снова нет ни одного ключа Gemini — ИИ не заработает, пока владелец не добавит настоящий.

12.09.2026 — заказ теперь проверяет стоп-лист живым запросом к Poster (`getProducts`) прямо перед отправкой, а не по нашему кэшу в `menu_items` (который обновляется только при подключении/вручную и мог быть устаревшим). Если что-то из корзины гостя сейчас в стопе — заказ не уходит на кассу вообще, гость видит конкретный список недоступных блюд и должен убрать их из корзины сам (автоматически не убираем). Прогнано: (1) реальный заказ на живом ресторане без стоп-листа — прошёл, `incomingOrderId` получен; (2) на момент проверки в реальном аккаунте не было ни одного блюда в стопе, поэтому негативный сценарий (гость получает 409) проверен через подмену `window.fetch` в браузере на реальной странице корзины — карточка корзины не очищается, показывает «Сейчас недоступно: {блюдо}». Полноценная живая проверка (официант реально ставит блюдо на стоп в Poster, потом гость пытается заказать) ещё не делалась — сработает сама, когда это случится в проде первый раз.

12.09.2026 — новая фича: ИИ-рекомендации по всему меню (не по одному блюду). Гость пишет, например, «нас трое, посоветуйте» — виджет «Не знаете, что выбрать?» на странице меню (`AskMenuRecommendation.tsx`) отправляет вопрос в новый `/api/recommend-menu`, который передаёт модели весь список доступных (не в стоп-листе) блюд заведения и просит подобрать сочетание под компанию, с той же защитой от выдумывания, что и в чате по одному блюду (рекомендованные названия сверяются со списком реальных блюд). По просьбе владельца — ИИ НЕ спрашивает про аллергии проактивно (осознанное решение: меньше трения, меньше юридического риска обещания), но если гость сам упомянул аллергию/непереносимость, промпт требует не рекомендовать блюда с неизвестным составом или этим аллергеном. Прогнано вживую с реальным ключом Gemini на реальном меню: на вопрос «посоветуйте на компанию из 3 человек» получен реальный ответ с разными блюдами из настоящего меню («Салат Цезарь», «Паста Карбонара», «Бургер с говядиной», «Плов по-узбекски», «Лимонад Клубника-Мята»), проверка на выдумывание прошла (иначе был бы фолбэк). Заодно поправлен нечестный текст на лендинге (`Features.item3`) — раньше он утверждал, что смена цены/стоп-листа на кассе видна гостю «в ту же секунду» (неправда, синк не живой); теперь текст честно описывает то, что реально работает — живую проверку стоп-листа перед отправкой заказа (сделано в этой же сессии чуть раньше).

Отдельный важный факт про экономику ИИ, обнаруженный в этой сессии: бесплатный тариф Gemini для превью-модели `gemini-3.8-flash` — всего **20 запросов в день на ключ/аккаунт** (не 1500, как было в нашем собственном дефолте `daily_limit` — это была непроверенная догадка). У владельца сейчас 2 ключа с разных Google-аккаунтов, итого ~40 запросов/день на двоих. Модель `gemini-3.8-flash` также периодически отдаёт живые 503 (Google перегружен) — воспроизведено многократно в этой сессии. На повестке: проверить реальный RPD у стабильной модели `gemini-2.5-flash` (ждём цифры от владельца) — если он ощутимо выше, стоит мигрировать `GEMINI_MODEL` в `lib/gemini/client.ts`; если нет — переходить на платный тариф Google Cloud (ориентир по цене: ~$0.75/1М входных, $3.75/1М выходных токенов, действует до 31.12.2026 — это дёшево относительно цены $15/мес). Наш собственный `daily_limit: 1500` (дефолт в БД и в `/api/admin/keys`) сейчас не отражает реальность и может маскировать реальные 429 от Google — стоит поправить после решения по модели/тарифу.

12.09.2026 — цепочка моделей Gemini вместо одной. Реальный факт, проверенный в дашборде AI Studio владельца: бесплатный лимит запросов/день — отдельный НА КАЖДУЮ МОДЕЛЬ, не общий на проект (`gemini-3.1-flash-lite` и `gemini-3.5-flash-lite` — по 500/день каждая, `gemini-3.8-flash` — всего ~20). Схема `gemini_api_keys` расширена колонками `model`/`priority` (миграция накатывалась владельцем вручную через SQL Editor — сервис-ключ Supabase не даёт выполнять DDL, только CRUD); один реальный ключ теперь превращается в 3 строки (по одной на модель из `lib/gemini/models.ts`), это делает `POST /api/admin/keys` автоматически. Новый `lib/gemini/callWithFallback.ts` перебирает все (ключ×модель) кандидаты по приоритету, пока один не ответит — итого до 6 попыток вместо 1 (`ask-dish` и `recommend-menu` оба переведены на него). Существующие 2 ключа задним числом разложены на все 3 модели скриптом (без повторного ввода значений).

Отдельная находка при проверке живьём: явное правило в промпте «обобщай категорию аллергена» **не сработало надёжно** — модель дважды порекомендовала блюда с пармезаном (молочный продукт) человеку с аллергией на молоко, хотя правило явно это запрещало. Добавлен детерминированный фильтр в коде — `lib/ai/allergenFilter.ts`: если в вопросе гостя есть слово про аллергию/непереносимость и распознана категория (молочное/глютен/орехи), блюда с совпадением по составу (и с неизвестным составом — по умолчанию считаются небезопасными) убираются из списка ДО того, как его увидит модель — она физически не может их порекомендовать. Проверено вживую через реальный браузер (не curl — на этой машине `curl -d` ломает кириллицу в теле запроса, из-за чего фильтр в первой проверке ошибочно не сработал; реальный фетч из браузера показал корректную работу): на «аллергия на молоко» модель порекомендовала только реально безмолочные блюда («Американо», «Лимонад Клубника-Мята», «Плов по-узбекски»), пасту с пармезаном и цезарь не упомянула вообще.
